1. Обзор и архитектурные принципы

Система АСОП строится на трёх независимых контурах аутентификации, каждый из которых оптимизирован под свой тип клиента и условия работы:

Клиент Метод Сетевое условие Где применяется
Веб-админка / Мобильное приложение пассажира JWT (OIDC через Keycloak) Всегда онлайн Управление системой, личные кабинеты, аналитика
Терминал (Android/Linux) mTLS + сертификат устройства Online ↔ Offline (до 12 ч) Приём оплаты, валидация, открытие смен, GPS-трекинг
Водитель MIFARE DESFire EV3 + PKI (ECDSA P-256) + PIN 100% Offline Аутентификация в терминале, открытие смены/рейса

Ключевые принципы

  1. Offline-first для терминалов: терминал способен работать без связи часами, накапливая сессии и транзакции локально.
  2. Аппаратная защита ключей: приватные ключи никогда не покидают защищённую среду (HSM для Root CA, Android Keystore/StrongBox для терминалов, чип DESFire для водителей).
  3. Zero-Trust на уровне устройств: каждый терминал и каждая карта водителя имеют криптографический паспорт, проверяемый через Root CA.
  4. Асинхронная архитектура Gateway: Gateway не пишет в БД. Он принимает запросы, валидирует аутентификацию/авторизацию, пушит команды в Kafka и возвращает 202 Accepted.
  5. Минимум изменений в БД: в схему добавляется только одно поле (ASOP_VEHICLES.CARRIER_ID → NULL). Новые таблицы не создаются.

2. Компоненты системы

2.1. Root CA (Корневой Центр Сертификации)

  • Назначение: единая точка доверия. Подписывает сертификаты терминалов и сертификаты водителей (на MIFARE-картах).
  • Хранение приватного ключа:
    • MVP: PKCS#12 файл + пароль в HashiCorp Vault / AWS Secrets Manager
    • Production: HSM (Thales Luna, YubiHSM 2, AWS CloudHSM) с защитой от физического вскрытия
  • Управление доступом: M-of-N (минимум 3 из 5 администраторов для подписи сертификата или отзыва)
  • Онлайн-операции: выполняются через Intermediate CA, который подписывается Root CA. Root CA физически отключён от сети.
  • Выходные артефакты: asop-root-ca.pem (публичный ключ), CRL (список отозванных сертификатов), Intermediate CA сертификаты.

2.2. Веб-клиенты и мобильные приложения (JWT + Keycloak)

  • Flow: Authorization Code Flow (веб), Authorization Code + PKCE (мобайл)
  • Токены:
    • access_token: JWT, TTL 5 мин, содержит sub, realm_access.roles, resource_access.asop-backend.roles
    • refresh_token: opaque, TTL 8 ч (веб) / 30 дн (мобайл), хранится в httpOnly cookie или Secure Storage
  • Валидация в Gateway:
    • JWT декодируется и проверяется локально через JWKS (/realms/asop/protocol/openid-connect/certs)
    • JWKS кэшируется в Gateway, обновляется каждые 60 сек
    • Никаких сетевых вызовов к Keycloak на каждый запрос
  • Авторизация: ролевая модель через Spring Security Reactive (hasRole, hasAuthority). Примеры ролей: SUPER_ADMIN, CARRIER_ADMIN, DISPATCHER, PASSENGER.

2.3. Терминалы (mTLS + сертификаты устройств)

  • Аутентификация устройства: Mutual TLS при каждом соединении с Gateway
  • Хранение приватного ключа терминала:
    • Android: AndroidKeyStore с флагом setIsStrongBoxBacked(true) (аппаратный SE, если доступен)
    • Linux/Embedded: TPM 2.0 или внешний YubiKey
  • Процесс регистрации терминала:
    1. При первом включении терминал генерирует пару ECC P-256 в Keystore
    2. Формирует CSR (POST /api/v1/terminals/register)
    3. Gateway подписывает CSR через Intermediate CA
    4. Терминал получает X.509 сертификат, сохраняет в Keystore
    5. Серийный номер сертификата фиксируется в ASOP_TERMINALS
  • Синхронизация (online): терминал запрашивает у Gateway:
    • Обновлённый CRL
    • Изменения в льготах (ASOP_USER_BENEFITS)
    • Изменения в тарифах (ASOP_TARIFF_RATES)
    • Чёрный список карт (ASOP_BLACKLISTS)
  • Offline-работа: терминал хранит локальные копии справочников. Сессии подписываются приватным ключом терминала и отправляются батчем при появлении связи.

2.4. Водители (MIFARE DESFire EV3 + PKI + Challenge-Response)

  • Криптография: ECDSA на кривой NIST P-256. Приватный ключ генерируется и хранится внутри чипа карты, физически не извлекаем.
  • Структура приложения на карте (AID: 0xD2760000850101):
    • File 0x01: X.509 сертификат водителя (подписан Root CA)
    • File 0x02: ECC Private Key (права: Sign Only, чтение запрещено)
    • File 0x03: Профиль водителя (driver_id, carrier_id, valid_from, valid_until)
  • Протокол аутентификации (NFC):
    1. Терминал генерирует случайный challenge (32 байта)
    2. Отправляет карте команду SignData(challenge)
    3. Карта подписывает challenge своим приватным ключом, возвращает подпись
    4. Терминал извлекает публичный ключ из сертификата (File 0x01)
    5. Терминал проверяет подпись локально
    6. Терминал проверяет срок действия сертификата и отсутствие UID в локальном CRL
    7. Водитель вводит PIN (второй фактор) → терминал сверяет хэш PIN с локальной базой
    8. При успехе → смена открыта
  • Персонализация карты (в депо): выполняется через NFC-ридер + ПК с ПО персонализации. Приватный ключ генерируется на карте, публичный отправляется на бэкенд для выпуска сертификата, сертификат записывается обратно на карту.

3. Детальные сценарии (Flows)

3.1. Аутентификация vs Авторизация в Gateway

Этап Вопрос Механизм Результат
Аутентификация Кто ты? Проверка подписи JWT (JWKS) или валидация Client Cert (mTLS) Principal / X.509Certificate
Авторизация Что тебе можно? Проверка ролей/скопов в токете, RBAC в Spring Security 200 OK / 403 Forbidden
Аудит Кто совершил действие? userId из JWT или terminal_serial из mTLS передаётся в Kafka-событие correlationId, userId в event

3.2. Открытие смены терминалом (полный цикл)

  1. Синхронизация (online): терминал загружает CRL, льготы, тарифы, чёрный список карт.
  2. Выбор транспорта: 
    SELECT VEHICLE_ID, VEHICLE_NUMBER, VEHICLE_NAME,
  CASE WHEN CARRIER_ID = :terminal_carrier_id THEN 1
       WHEN CARRIER_ID IS NULL THEN 2 ELSE 3 END AS priority
FROM ASOP_VEHICLES
WHERE CARRIER_ID = :terminal_carrier_id OR CARRIER_ID IS NULL
ORDER BY priority, VEHICLE_NUMBER;
  3. Выбор маршрута (M:N через договоры): 
    SELECT DISTINCT r.ROUTE_ID, r.ROUTE_NUMBER, r.ROUTE_NAME
FROM ASOP_ROUTES r
JOIN ASOP_CONTRACT_ROUTES cr ON cr.ROUTE_ID = r.ROUTE_ID
JOIN ASOP_CONTRACTS c ON c.CONTRACT_ID = cr.CONTRACT_ID
WHERE c.CARRIER_ID = :terminal_carrier_id AND c.STATUS = 'ACTIVE';
  4. Аутентификация водителя: NFC Challenge-Response + PIN (2FA).
  5. Создание сессии: терминал генерирует SESSION_ID (UUIDv7), фиксирует STARTED_AT_LOCAL, PATH_ID, VEHICLE_ID, DRIVER_UID.
  6. Локальная подпись: терминал подписывает хэш сессии своим приватным ключом (SHA256withECDSA).
  7. Работа офлайн: накопление транзакций в локальной SQLite/Room.
  8. Синхронизация: при появлении сети терминал отправляет батч сессий на Gateway → Kafka → session-service.

3.3. Персонализация MIFARE-карты водителя

  1. Администратор помещает пустую DESFire EV3 на NFC-ридер.
  2. ПО персонализации аутентифицируется как Admin (Master Key).
  3. Создаётся приложение ASOP, генерируется ECC P-256 ключевая пара внутри чипа.
  4. Публичный ключ отправляется на driver-card-service.
  5. Бэкенд формирует X.509 сертификат (CN=driver_id, OU=carrier_id, O=ASOP), подписывает через Root CA.
  6. Сертификат записывается в File 0x01, профиль в File 0x03.
  7. Карта выдаётся водителю, запись в журнал.

3.4. Отзыв сертификата и обновление CRL

  1. Администратор отзывает карту/терминал в веб-админке (POST /api/v1/certificates/{serial}/revoke).
  2. Бэкенд помечает сертификат как REVOKED, добавляет серийный номер в CRL.
  3. CRL подписывается Root CA, публикуется на Gateway.
  4. Терминалы при следующей синхронизации загружают обновлённый CRL.
  5. При попытке аутентификации терминал сверяет UID/Serial с локальным CRL → доступ запрещён.

4. Изменения в схеме БД

Единственное изменение: поле CARRIER_ID в таблице ASOP_VEHICLES становится nullable для поддержки общего пула транспорта (реальный кейс: аренда/передача ТС между перевозчиками). 
ALTER TABLE ASOP_VEHICLES
    ALTER COLUMN CARRIER_ID DROP NOT NULL;

COMMENT ON COLUMN ASOP_VEHICLES.CARRIER_ID IS
    'Перевозчик-владелец. NULL = общий пул транспорта, доступный любому перевозчику через договор или временную передачу.';
Важно: таблицы ASOP_TERMINAL_CERTIFICATES, ASOP_DRIVER_CARDS, ASOP_VEHICLE_TRANSFERS в схему не добавляются. Управление сертификатами и картами ведётся через внешние системы/журналы, а в БД фиксируются только бизнес-сущности и ссылки на серийные номера/UID при необходимости.

5. Защита от атак

Атака Вектор Митигация
Клонирование карты Снятие дампа памяти DESFire EV3: ключи в аппаратном SE, UID защищён от чтения
Replay-атака Перехват и повтор NFC-ответа Случайный challenge + timestamp + одноразовая сессия
Кража карты водителя Физическое хищение PIN как второй фактор + удалённый отзыв через CRL
Компрометация терминала Root/доступ к ОС Приватный ключ в Keystore/StrongBox, не извлекаем. Данные сессий подписываются, но ключ не покидает чип
Подмена Root CA MITM при обновлении прошивки Root CA public key зашит в образ прошивки, проверяется через хэш
Компрометация Root CA Утечка приватного ключа CA HSM + M-of-N + offline хранение + процедура emergency rotation
Фабрикация транзакций Подмена данных на терминале Каждая сессия подписывается ключом терминала. Gateway валидирует подпись перед приёмом в Kafka

7. Ключевые принципы и рекомендации по внедрению

  1. Не хранить приватные ключи в БД. БД хранит только бизнес-данные, ссылки на серийные номера сертификатов и UID карт. Криптография остаётся на устройствах и в HSM.
  2. CRL должен обновляться превентивно. Терминал не имеет права открывать смену, если карта водителя находится в локальном CRL.
  3. Offline-окно ограничено 12 часами. После истечения EXPIRATION_TIME сессии терминал обязан синхронизироваться, иначе блокирует приём оплат.
  4. Конфликты синхронизации решаются по timestamp. Если два терминала отправили сессии с одинаковым VEHICLE_ID в overlapping timeframe, session-service помечает одну как CONFLICT и требует ручной проверки диспетчером.
  5. Root CA rotation планируется заранее. За 30 дней до истечения срока Root CA выпускается новый, прошивки терминалов обновляются через OTA, старые сертификаты переиздаются.
  6. Тестирование криптографии обязательно. Использовать njadesfire или нативный IsoDep для эмуляции DESFire EV3 в CI. Проверять challenge-response, подпись сессий, валидацию CRL.
  7. Логирование аутентификации. Все успешные и неуспешные попытки входа (веб, терминал, NFC) фиксируются в audit-логе с correlationId для расследования инцидентов.
