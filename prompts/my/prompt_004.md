давай отладим тогда промпт для асоп большими мазками надо:

1. Создать таблицу трипл-дес ключей asop_3des_keys, ее надо создать. Занести в скрипт
   infrastructure/db-migrations/asop_schema.sql Структура:
   UUID 7 - первичный ключ 3des ключ, CREATED_AT TIMESTAMPTZ NOT NULL DEFAULT NOW (), UPDATED_AT TIMESTAMPTZ NOT NULL
   DEFAULT NOW (), DELETED_AT TIMESTAMPTZ, VERSION BIGINT последние 4 поля для загрузки таблицы на терминал добавить эту
   таблицу к общему механизму закачки таблиц/справочников с сервера на андроид-терминалы, как чанками так и полным
   набором Из данной таблицы записи принципиально физичиски удалять нельзя, только метить на удаление. Данные по
   трипл-дес ключам в самой таблице шифровать публичным ключом сервера, который брать из крипто-сервиса (возможно надо
   на нем сделать ендпоинт для этого), перед отправкой на терминал рассшифровываем крипто-сервисом (его приватным
   ключом)
   При отправке трипл-дес ключей из сервера на терминал, берем публичный ключ из сертификата X.509 терминала, который
   лежит на сервере в ASOP_TERMINAL_CERTS.CERT_DATA (PEM). Трипл-дес ключи в таблице для отправки на терминал шифруем
   публичным ключом терминала. Записи по трипл-дес ключам только добавляются в табилицу и никогда физически не
   удаляются, только метятся на удаление. Перешифровка ключом терминала происходит в сервисе оркестратор.
2. Цель: безболезненно доставить на терминал ключ для работы с картой (DESFire/3DES), не храня его в открытом виде.
   Участники:

    - Сервер (ASOP backend) — знает ключ карты (поле 3DES, 24 байта).
    - Терминал (Android) — имеет пару ключей EC P-256: приватный ключ хранится у него (в keystore), публичный ключ
      заранее известен серверу (передан при выпуске сертификата/регистрации). Шаги:
        1) Сервер: берёт значение ключа карты cardKey (24 байта 3DES) и публичный ключ терминала T_pub.
        2) Сервер шифрует:
           ciphertext = ECIES_encrypt (T_pub, cardKey). Т.к. T_pub — EC-ключ, шифрование делается не «сырым RSA», а
           через ECDH + AES-GCM (ECIES): генерируется эфемерная ключевая пара, выводится общий секрет S = ECDH
           (term_pub, ephemeral_priv), cardKey шифруется AES-GCM ключом, производным от S.
        3) Сервер отправляет ciphertext на терминал.
        4) Терминал распадаёт обочно: cardKey = ECIES_decrypt (term_priv, ciphertext).
        5) Терминал хранит: НЕ кладёт cardKey в открытом виде. Сохраняет в локальную таблицу только зашифрованное
           значение. Желательно — повторно зашифрованное уже локальным способом (например, через Android Keystore AES
           key, или перешифрованное третьим ключом), так чтобы расшифровка возможна только на терминале. Важное
           уточнение («подводный камень» в твоей формулировке): «зашифровать 3DES-ключ публичным EC-ключом» реализуемо
           только через ECIES (ECDH + AES-GCM), а не через «raw RSA». Разница:
    - RSA умеет шифровать публичным ключом «в лоб».
    - EC имеет только обмен ключами (ECDH); шифрование данных публичным ключом достигается через ECIES-схему. Поэтому
      строго это записывается так:
      Сервер заворачивает 24-байтный 3DES-ключ карты через ECIES (эфимерный ключ: ephemeral EC-ключ + ECDH на T_pub →
      AES-GCM) и передаёт ciphertext. Терминал расшифровывает своим приватным EC-ключом и сохраняет cardKey в локальной
      БД только в зашифрованном виде (перешифровка через Android Keystore), доступен для работы с картой лишь
      расшифрованным в момент транзакции.
    - Терминал создает пару ключей при регистрации терминала, публичный отсылает серверу, сервер его подписывает, отдает
      обратно сертификат, и так же этот сертификат сохраняет себе в таблице У сервера есть публичный ключ терминала.
      Сервер держит 3дес ключи карт в таблице у себя на сервере в защифрованном виде, зашифрованы они публичным
      серверным ключем. Когда 3дес ключи надо передать на терминал, сервер (оркестратор) выгребает их из таблицы,
      расшифровывает приватным серверным ключом, через крипто-сервис, так как это мастер система, хранящая приватный
      ключ. Далее оркестратор берет из базы сертификат с публичным ключом терминала (UUID 7 терминала придется передать
      вместе с регион_ид и последней версий справочников на терминале), публичным ключом терминала оркестратор шифрует
      3дес ключи в таблице и отправляет это терминалу. Терминал, складывает все это в свою локальную базу, и когда
      требуются операции с майфер картой, вытаскивает 3дес ключи, расшифровывает из своим приватным ключом, и делает
      карточные операции одним из подходящих ключей, если подошел 3дес ключ не самый свежий из таблицы, то терминал
      принудительно менят ключ на карте на последний в таблице.
    -
        1. Терминал генерирует AES-ключ в Android Keystore (PURPOSE_ENCRYPT | PURPOSE_DECRYPT, неэкспортируемый,
           аппаратно защищённый в TEE)
        2. 3DES-ключи карт приезжают с сервера по mTLS (уже зашифрованный канал) — в дельта/полной выкачке, вместе со
           справочниками
        3. Терминал при приёме шифрует 3DES-ключи Keystore-AES и хранит в Room только зашифрованными
        4. При карточных операциях — терминал просит Keystore расшифровать (AES-ключ наружу не выходит,
           шифрование/дешифрование происходит внутри Keystore API)
        5. Один AES-ключ на все 3DES-ключи в таблице Ключевой момент: Keystore-AES-ключ никогда не покидает Keystore —
           приложение вызывает Cipher.init (ENCRYPT, keystoreKey) и Keystore сам шифрует/расшифровывает данные, отдавая
           только результат. Сырой AES-ключ недоступен ни приложению, ни adb root (на userdebug — теоретически доступен
           через Keystore-эксплойты, но это уже продвинутая атака).
3. Создать таблицу asop_config_params. Занести в скрипт infrastructure/db-migrations/asop_schema.sql Структура:
   UUID 7 - первичный ключ регион, может быть null организатор перевозок, может быть null перевозчик, может быть null
   дистрибутер, может быть null контрольно ревизионная служба, может быть null JSONB - жсан с параметрами параметры
   перекрываются, базовые, где все нал, параметры региона перекрывают базовые, организатора перекрывают регион и так
   далее, перекрываются только те, что указаны, если не указаны, то берется из более низкого по иерархии
4. Сделать редактирование обоих таблиц в админке, но в разных пунктах меню: "Ключи 3des" и "параметры асоп"
   При редактировании ключей показывать зашифрованные ключи, и сделать кнопку добавить с ручной генерацией ключа. Ключ
   создается, шифруется публичным ключом крипто-сервиса, заноситься в таблицу, и кнопка для кдаления, которая метит
   записи DELETED_AT
5. В сервисе оркестратор надо создать шедуллер, который будет автоматически добавлять запись о новом ключе. Параметры,
   такие как шаблон крон новой записи , старт шедуллера и его остановка вынести в конфигурационные файлы оркестратора, и
   сделать настраиваемыми из программы веб-админ (в отдельной минюшки слева - "параметры асоп"). Шедуллер генерит
   переодически трипл-дес ключи. Шедуллер берет параметры из самого высокого уровня, когда регион, организатор
   перевозок, и т.д. все нал.
6. Когда данные по трипл-дес ключам приходят на терминал и терминал их накатывает, то терминал накатывае данные ключей
   не больше чем за 5 последних лет, параметр этот тоже должден быть настраиваемым из админки. И вот терминал, физически
   из своей базы удаляет записи, помеченные на удаление.
7. На терминале трипл-дес ключи упорядочены по UUID 7 (первый самый последний). Применятся к майфер-картам будут
   последовательно, промпт для этого будет потом, не сейчас.
8. Для целей отладки в процедуре, которая будет выдавать очередной случайный ключ трипл-дес сделай разработчиский режим,
   в котором процедура эта бы выдавала одни единственный заранее известный ключ (сгенери его один раз), ключ этот
   задокументируй. В процессе разработки, отладки и тестирования мы должны пользоваться единственным ключом, дабы не
   тратить карты, которые стоят денег.
