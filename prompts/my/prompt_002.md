Инкрементальная дельта-синхронизация запускается андроид терминалом в шедуллере раз в час.

Терминал сообщает свои carrier_id и region_id при запросе синхронизации. Всегда, они у него есть на момент запроса
обновления.

все справочники для отсылки на терминал фильтруются по регионом и перевозчиком, если такие связки есть, или до них можно
дотянуться в базе из срправочника. Если связки данных справочника с регионом и/или перевозчиком нет, то передаем весь
справочник (согласно технологии incremental Delta Sync чанками, отмеченной ранее)

синхронизация происходит по полю UPDATED_AT TIMESTAMPTZ NOT NULL записи из справочников/таблиц физически не удаляются, а
лишь ментяться для удаления при помощи поля deleted_at TIMESTAMPTZ если оно NULL то запись действительная, если там дата
удаления, то запись удалена в дату и ремя, которое хранит поле.

если в српавочнике нет поля UPDATED_AT TIMESTAMPTZ NOT NULL то добавить и построить по нему индекс если в справочнике
нет поля deleted_at TIMESTAMPTZ то добавить и приделать триггер BEFORE DELETE, который делает UPDATE (устанавливает
deleted_at) и возвращает NULL (отменяет удаление).

При установке deleted_at обязательно обновлять updated_at.

организовать в слое микросервисов (те что за кафкой ) еще один микросервис - оркестратор. Оркестратор общается с другими
сервисами через TLS и REST, синхронно. Оркестратор выполнен в той же парадигме как и все остальные микросервисы, смотри
документацию в папке ./doc/*.md и контекст agents.md

В отекстраторе сделать шедуллер, который будет физически удалять помеченные к удалению записи с переодичностью час, и
удалять только записи полугодовой дальносить и старше. Как обходить при этом триггер, придумай сам.

Андроид переодически формирует асинхронный запрос к серверу на обновление справочников, собирая из своей локальной базы
последние UPDATED_AT всех справочников, требующих синхронизации. Сервер отдает ответ мгновенно - "Accepted" и
идентификатор для выкачки результата. Далее в цикле переодически опрашивает сервер о готовности, Все асинхронно, в
менеджере заданий на взаимодействие с сервером.

С сервера может в ответ прийти по одному запросу с одинм идентификатором много чанков ответа, на разные справочники и с
разными страницами этих справочников. Андроид собирает весь ответ целиком и накатыват справочники в свою локальную базу.
При любом сбое в этом процессе (не дождались чанка в телечнии определенного тайм-айта, например, или по любой другой
причине) андроид забывает про запрос обновления справочников и через некоторое время фромирует другой такой же.

Асинхронный запрос обновления справочников приходит на сервер в гейтвей. Гейтвей делает mTLS авторизацию, отправляет
запрос в кафку, и мгновенно отвечает андроиду, что запрос принят, и отдает идентификтор для получнеия ответа. Из кафки
запрос вычитывает оркестрарот, опрашивает другие микросервсы являющиеся мастер-системами для определенных справочников
по условию "больше чем UPDATED_AT" и фильра по региону и перевозчику, собирает всю информацию, если длинна выходного
сообщения больше 50кб (способ определения ниже), то формирует чанки, нумерует их, и отправляет в редис в формате
Protobuf для дальнейшей выкачки терминалом. На редисе чанки лежат по ключи идентификатора для получения ответа и номеру
чанка. В редисе так же по ключу идентификтора ответа (одного, без номера чанка) будет лежать информация об общем
количестве чанков. Идетификатор ответа генерирует гейтвей.

### Алгоритм формирования чанков (Chunking by size)

При сборке ответа оркестратор должен разбивать данные на чанки строго не более 50 КБ, используя точное измерение размера
Protobuf без лишнего аллоцирования памяти:

1. Итерироваться по записям из БД и добавлять их (в виде Protobuf-объектов) во временный буфер (List).
2. После добавления каждой записи вычислять текущий размер буфера через метод `message.serializedSize` (это работает
   мгновенно и не создает `byte[]` в памяти).
3. Если `serializedSize > 50_000` байт:
    - Убрать последнюю добавленную запись из буфера.
    - Сериализовать текущий буфер в байты (`toByteArray()`) и сохранить как готовый чанк.
    - Начать новый пустой буфер и добавить в него ту самую "лишнюю" запись, которая вызвала превышение.
4. По завершении итерации по БД сериализовать остаток буфера в байты и сохранить как последний чанк.

### конец Алгоритм формирования чанков (Chunking by size)

Сделать на андроиде меню с принудительной выкачкой всех справочников полностью. Для этого добавить в докер композ
хранилище MinIO, используя AWS S3 SDK на бэкенде и обычный HTTP-клиент на Андройде. По асинхронному запросу с андроида,
выдать ответ, что принять, отдать идентификатор отвера. Андроид переодически опрашиват ответ, в ответе от серера
приходит ссылка на S3 с архивированным файлом со всеми справочниками/таблицами. За формирование этого файла отчечает
оркестратор.

Полная выгрузка справочников осуществляется при необходимости вручную из меню.

Структура локальной базы данных андроид совпадает с серверной базой данных infrastructure/db-migrations/asop_schema.sql
с адоптацией к реалиям андроида (SQLite через Room (androidx.room:2.6.1)) и к тем сущностям, которые туда уже добавлены
(Три сущности: PendingEventEntity, SessionEntity, TransactionEntity в AppDatabase (db/AppDatabase.kt).)

Если дельта слишком большая (например, терминал был офлайн месяц) то продолжаем Инкрементальную дельта-синхронизацию.
Шифрование Protobuf-файлов в MinIO не надо, будет HTTPS. Формат архива для полной выгрузки - ZIP с отдельными файлами на
каждый справочник. Компрессия (gzip) для Protobuf-данных не нужна.

### Сжатие данных (Компрессия)

1. **Для полной выгрузки (ZIP):** Использовать стандартный ZIP-архив (алгоритм Deflate). Внутри архива хранить "сырые"
   `.pb` (Protobuf) файлы без предварительного Gzip-сжатия, чтобы избежать двойного сжатия.
2. **Для дельта-синхронизации (Kafka/HTTP):** Не использовать ручное Gzip-сжатие в коде приложения.
    - Для Kafka использовать встроенное сжатие топиков (LZ4/Zstd).
    - Для HTTP-ответов (polling от Android) включить встроенную компрессию Spring Boot
      (`server.compression.enabled=true`), чтобы сервер сам сжимал Protobuf-ответы на лету.
