# Промпт 014: Поездки в MIFARE Classic (карта-кошелёк), пополнение, льгота

## 1. Контекст и текущий формат карты (уточнено)

Текущий формат **VCM1** (промпт 008/009): используется **только сектор 1**, 3 data-блока по 16 байт (48 байт):

```
block 0:  "VCM1" magic [0..3] + bitmask UInt16 LE [4..5] + reserved/zeros [6..15]
block 1:  cardId UUID v7 binary (16 байт, MSB-first)
block 2:  entityUuid UUID v7 binary (16 байт), zeroed у PASSENGER_ANONYMOUS
```

Сектор 2 и далее — зарезервированы, **не используются** (VCM1 = только сектор 1).

## 2. Что меняем (решение Q1 = вариант A, без смены версии формата)

В **block 0** сектора 1 задействуем **2 ранее свободных байта [10..11]** для хранения **количества поездок** (`tripsLeft`, UInt16 LE). Версия формата остаётся VCM1 (`"VCM1"`), чтение старых карт с нулями в [10..11] = 0 поездок — обратно совместимо.

Итого block 0:
```
[0..3]  "VCM1" magic
[4..5]  bitmask UInt16 LE
[10..11] tripsLeft UInt16 LE
[6..9], [12..15] reserved/zeros
```

## 3. Функциональные требования

### 3.1 Активация карты пассажира
При активации карты пассажира (персональной `PASSENGER` и неперсональной `PASSENGER_ANONYMOUS`) записывать `tripsLeft = 0`.

### 3.2 Пополнение карты (режим «Пополнить карту»)
- На терминале новый режим в меню **«Пополнить карту»**.
- Авторизация оператора — картой **дистрибьютора** (`DISTRIBUTOR_ADMIN` / `DISTRIBUTOR_DISPATCHER`) или любого админа выше по иерархии (`AUTHORIZATION_MATRIX`).
- Ввести число N (количество поездок).
- Записать на карту: `tripsLeft = текущее + N`.
- Разрешаем пополнение **и персонализированных карт с льготой** (поездки просто накапливаются, но при наличии льготы не списываются) — решение Q4.

### 3.3 Валидация пассажира на рейсе
Логика при `tap` пассажирской карты:

1. Определить, **персонализирована ли карта** (entity != null и role относится к пассажиру: `PASSENGER` или `PASSENGER_ANONYMOUS`). Иные роли (водитель/админ/КРС и т.п.) — не валидация пассажира.
2. **Если карта персональная (`PASSENGER`)** — проверить наличие льготы:
   - Связка: `cardId` (из block 1) → `ASOP_CARDS.USER_ID` → `ASOP_USER_BENEFITS` (активные) → `ASOP_BENEFITS`.
   - Активная льгота = `deleted_at IS NULL` и (`valid_until IS NULL OR valid_until > now`) и (`valid_from IS NULL OR valid_from <= now`).
   - Если льгот несколько — берём **любую первую** (решение Q5).
   - **Льгота есть** → проезд валидируем, поездки **НЕ списываем** (`tripsDebited = 0`), в отчёт пишем `benefitId`.
   - **Льготы нет** → действуем по сценарию для неперсональной (п. 3.3.3).
3. **Иначе (неперсональная `PASSENGER_ANONYMOUS` или персональная без льготы):**
   - Читаем `tripsLeft` с карты.
   - Если `tripsLeft > 0` → отнимаем 1, записываем `tripsLeft = tripsLeft - 1` на карту, проезд валидируем, `tripsDebited = 1`.
   - Если `tripsLeft == 0` → **не валидируем** проезд, сообщаем отказ (решение Q7).

4. **Результат в текущую сессию рейса** — фиксируем факт валидации (и успех, и отказ из-за 0 поездок), с информацией о снятых поездках и применённой льготе. Отправляем на сервер по существующему офлайн-пайпу (PendingEvent → SyncWorker → gateway → Kafka → card-service).

### 3.4 Контракт передачи данных (решение Q2, Q3)
- **Зеркально поездки на сервере НЕ храним** — за поездками следит только карта (Q2).
- В `metadata` транзакции укладываем **JSON** `{"tripsDebited": <int>, "benefitId": "<uuid|null>"}` (Q3-б).
- `transactionResultId` оставляем **«Зафиксировано (без списания)»** (`00000000-0000-0000-0000-000000000903`) для всех валидаций (и платной, и льготной, и отказа), `amount = 0.0`, `currency = "RUB"` (Q3).
- Итоговый формат `metadata` — JSON-строка, например `{"tripsDebited":1,"benefitId":null}` или `{"tripsDebited":0,"benefitId":"<uuid>"}`. Для отказа `{"tripsDebited":0,"benefitId":null}` с отдельной пометкой отказа (см. 3.5).

### 3.5 Отказ из-за 0 поездок (Q7)
Отказ фиксируем и отправляем на сервер. Способ пометки в рамках MVP: в `metadata` добавляем флаг, например `"declined":true`, либо отдельный `transactionResultId` «Отказано (нет поездок)». **Согласовать формат** — см. п. 6 open-вопрос.

## 4. Web-admin («Смены и рейсы» → «Валидации»)
В таблице валидаций пробивать из `metadata`:
- `tripsDebited` (снятые поездки, включая 0),
- применённая льгота (`benefitId` → имя льготы из `ASOP_BENEFITS`),
- пометка отказа (если применимо).

## 5. Терминал, экран «Прочитать карту»
В меню **«Прочитать карту»** для MIFARE Classic показывать отдельным полем **«Количество поездок»** (`tripsLeft`).

## 6. Open-вопросы / допущения
- Формат пометки «отказ из-за 0 поездок» (флаг в `metadata` vs отдельный `transactionResultId`) — выбрать консистентно, согласовать в коде.
- Пополнение: max допустимое значение `tripsLeft` (переполнение UInt16) — что делать при +N сверх 65535.
- Пополнение и запись на активную VCM1-карту: не трогать block 1/2/bitmask — только байты [10..11] (безопасный write счётика).
- История пополнений на терминале/сервере — в MVP не обязательна (сервер поездки не хранит, Q6 покрен).
