## 4. Устранение узкого горла crypto-service (production)

**Проблема:** crypto-сервис — единственный обладатель приватного ключа, которым
расшифровываются секреты (3DES-ключи карт, персональные данные). Это:
- single point of failure — падение сервиса останавливает любую расшифровку;
- bottleneck под нагрузкой (RSA/ECC медленные, один инстанс = очередь);
- один ключ = компрометация всех данных разом;
- потеря ключа без реплики = криптографическая потеря данных навсегда;
- ротация ключа требует массовой перешифровки через центральный сервис.

### Что сделать на проде (TODO)

1. **Envelope encryption (DEK)** — на запись/пользователя свой DEK, данным
   DEK зашифровывает данные; master-ключ crypto-сервиса расшифровывает только
   маленький DEK, а не все секреты. Нагрузка и последствия утечки снижаются.
2. **Key-wrapping / TMS + HSM** — 3DES-ключи карт не хранить в БД напрямую,
   а отдать HSM/Key-Vault (он расшифровывает сам, ключ наружу не отдаёт).
3. **Репликация/HA ключа в trust-region** — держать несколько безопасных
   копий ключа + распределённая расшифровка (развьюkrypting) вместо одного
   инстанса; не потерять данные при падении/компрометации одного узла.
4. Итог: не держать один большой секрет в одном месте. Разбить — данные
   своими ключами, ключи отдельно, доступ у нескольких надёжных хранителей.

Когда реализовать: при переходе на production / Kubernetes.
